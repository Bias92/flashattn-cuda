# Causal masking, RTX 4060 Ti, 2026-09-14

Causal support was added to `cuda/attention_forward.cu` as a `CAUSAL` template parameter.
A causal block stops its K/V loop at `min(N, q_block + BR)` and masks only the block that
crosses the diagonal; blocks fully below it take the unmasked path. With `CAUSAL=false`
the added code compiles out, and the register counts for those instances are unchanged
(82 / 82 / 82 / 94 before and after), so the dense numbers are not affected by the change.

## Environment

RTX 4060 Ti, driver 595.97, WSL2 Ubuntu 24.04.1, Python 3.12.3, torch 2.10.0+cu128, CUDA 12.8.
Build flags `-O3 --use_fast_math -gencode=arch=compute_89,code=sm_89`.

Register use per instance (WRITE_L, FULL_TILES, CAUSAL), all with LOCAL 0 and STACK 0:

    0,0,0 REG 82    0,1,0 REG 82    0,0,1 REG 85    0,1,1 REG 88
    1,0,0 REG 82    1,1,0 REG 94    1,0,1 REG 85    1,1,1 REG 88

## Correctness

`python3 tests/test_attention_forward.py`: 37/37 passed, covering both mask modes across the
full and guarded paths, N from 1 to 4096, fp16-direct inputs and large-logit stress cases.

Causal output was also compared against `F.scaled_dot_product_attention(..., is_causal=True)`
on the FlashAttention backend: max absolute difference 4.88e-04 at N = 64, 128, 256, 512,
1024, 2048, 4096, which is fp16 rounding.

## Why causal comes out ahead

The kernel PyTorch launches is the same instantiation for both mask modes:

    pytorch_flash::flash_fwd_kernel<Flash_fwd_kernel_traits<64, 128, 128, 4, ...>>

so its query block is 128 rows and its K/V step is 128 columns. A 128x128 diagonal block is
half wasted under a causal mask. This kernel uses a 64-row query block and 32-column K/V
steps, so the masked-out fraction of the work is smaller. The same small tile is what leaves
it slightly behind on the dense rows, where PyTorch's larger tile gets more reuse.

FLOPs counted as 4·N²·D·H, halved for causal.
