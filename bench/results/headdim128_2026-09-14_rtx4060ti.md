# Head dimension 128, RTX 4060 Ti, 2026-09-14

Head dim 128 now works: the kernel is instantiated for both 64 and 128 and the host picks
one at run time. Output matches `scaled_dot_product_attention` to fp16 rounding, and the test
suite is 47/47 across both head dims, both mask modes, grouped-query and the guarded path.

It is slower than both SDPA backends at 128, and a sweep of the tile parameters did not close
the gap.

## What had to change

- `KVStager` was written for D=64, BC=32 and 128 threads: each thread copied one column chunk
  of two K rows and two V rows. It now walks `BC / (THREADS / (D/8))` row steps, which covers
  any of these shapes and leaves the D=64 schedule as it was.
- Q is staged in shared memory before the loop and borrows the second K/V stage, so `BR` must
  not exceed `2*BC`. That was implicit; BC=16 with BR=64 overran shared memory and produced an
  illegal access. It is a `static_assert` now.
- Shared memory is dynamic instead of a static array. A static `__shared__` array is capped at
  48 KB per block, and the larger tiles need more: BC=64 double-buffered at D=128 is 69632 B
  and ptxas rejected it with "uses too much shared data (0x11000 bytes, 0xc000 max)". The host
  now passes the size at launch and raises `cudaFuncAttributeMaxDynamicSharedMemorySize` when
  it is above 48 KB.

`ATTN_BR`, `ATTN_BC` and `ATTN_DOUBLE_BUFFER` are build-time knobs, defaulting to the
configuration the D=64 numbers were measured with.

## Tile sweep at D=128

B=1, H=32, H_kv=8, fp16, rotating order, median of 5. TFLOPS counted as 4·N²·D·H, halved for
causal.

| config | causal 2048 | causal 4096 | dense 2048 | dense 4096 |
|---|---:|---:|---:|---:|
| BR=64 BC=32 double (default) | 1.0165 (33.8) | 3.7937 (36.2) | 1.7723 (38.8) | 6.9727 (39.4) |
| BR=64 BC=64 double | 1.1603 (29.6) | 4.2108 (32.6) | 2.0782 (33.1) | 7.8583 (35.0) |
| BR=128 BC=64 double | 1.0862 (31.6) | 3.8952 (35.3) | 1.9082 (36.0) | 7.1113 (38.7) |
| BR=64 BC=64 single | 1.0552 (32.6) | 3.8921 (35.3) | 1.9808 (34.7) | 7.7313 (35.6) |
| PyTorch flash | 0.8867 (38.7) | 3.3345 (41.2) | 1.7469 (39.3) | 6.6932 (41.1) |

The default configuration is the best of the four and still trails flash by 1.5% on dense at
N=2048 and by about 14% on causal.

## Why the bigger tile did not help

PyTorch switches its own tile at this head dimension: `Flash_fwd_kernel_traits<64, 128, 128, 4>`
at D=64 becomes `<128, 64, 64, 4>` at D=128, so a 64-row query block with 64-column K/V steps is
what their tuning picked. Matching that shape here made things worse, both double- and
single-buffered.

What does not change with the tile is the output accumulator. Each warp holds a 16 x D output
tile in registers, which is 32 registers at D=64 and 64 at D=128, and the kernels report 166
registers at D=128 against 94 at D=64. Every K/V block also rescales that whole accumulator.
Neither cost moves when BR or BC change, which is consistent with the sweep being flat-to-worse.
Getting D=128 competitive looks like a question of how O is held and rescaled, not of tile size.

## Scope

One GPU, fp16, forward only, N_q = N_kv. The D=64 numbers in the README and the other records
are unaffected: the eight D=64 instances keep their register counts and the default build
parameters are unchanged.
