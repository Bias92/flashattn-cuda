## 1. Before and after: what the new features cost the old paths

with a paired A/B against the committed kernel (HEAD 32056b7, contiguous inputs), not against
FlashAttention. Column values are time relative to HEAD (1.0 = HEAD, lower is faster), median of
20 paired reps in rotating order; `v5` is the median of its three runs.

Causes, each isolated by an experiment that changed one thing (sources and outputs in
`raw_2026-09-20_v5/`):

1. v3 (2026-09-19, never measured as final): the K/V stager located rows with a hoisted
   multiply and selected the source pointer for rows past N. Guarded causal inputs lost
   3.7-7.9% against HEAD. Fixed in v5: the hoisted form only when every row exists
   (full tiles), a clamped row index otherwise (`bisect_run1.txt`, `ab_guarded_run1.txt`).
2. v6, guarded causal at D=128, +1.9 to +4.9% against v5: the second length. With `N_kv`
   forced equal to `N_q` inside the v6 kernel the loss disappears (`ab_v6sq_run1.txt`, column
   v6sq). v7 compiles square launches (`N_q == N_kv`) with one length (template flag `SQUARE`).
3. v6, dense with L on aligned inputs, +3.0 to +3.5% against v5: handing K, V and their
   strides to the kernel as one by-value struct. The same edit applied to v5 alone reproduces
   it, with or without `__restrict__` on the members (`ab_struct_run1.txt`, columns st, stR).
   v7 passes the members of the K/V source as separate kernel arguments.

What is left against v5: every entry of both v7 runs is within -0.3% and +0.7%. Aligned causal
D=64 sits at +0.1 to +0.6% in both runs; the v5 column itself moves by up to 0.6% between runs.

What is left against HEAD (v7 run 2 minus 1): aligned causal is 1.4-4% faster, guarded D=128
dense 8% faster, guarded causal 0.8-2.9% slower, dense forward_only at H=32/8 N=2048 3.6%
slower. The slower entries came with the stride generalization (HEAD had the row layout as a
compile-time constant). A bisect of v5 (`bisect5_run1.txt`) puts about 2% on one non-GQA shape
on the run-time K/V row stride and finds no single cause for the D=128 part. No specialization
for contiguous inputs was added.

Correctness of v7: tests/test_attention_forward.py 66/66, tests/test_attention_chunked_paged.py
40/40, compute-sanitizer memcheck 0 errors and racecheck 0 hazards on both files
(`docs/serving/prefill_campaign_2026-09-20/sanitizer/v7_*.log`).

## 3. Is PyTorch's vendored FlashAttention a weak opponent?

PyTorch pins the FlashAttention-2 kernels it vendors at upstream v2.7.4, and every "vs flash"
number above is against that. If upstream had made FA2 faster on Ada since, the comparison
would be against a weaker opponent than the real thing.

It has not. Diffing the PyPI source of 2.7.4.post1 against 2.8.3, the files that decide Ada
forward performance are byte-identical:

| file | what it decides | 2.7.4 vs 2.8.3 |
|---|---|---|
| `csrc/flash_attn/src/kernel_traits.h` | Br, Bc, warps per head dim | identical |
| `csrc/flash_attn/src/flash_fwd_hdim64_fp16_sm80.cu` | the D=64 fp16 instantiation | identical |
| `csrc/flash_attn/src/flash_fwd_hdim128_fp16_sm80.cu` | the D=128 fp16 instantiation | identical |
| `csrc/flash_attn/src/softmax.h` | the online softmax | identical |
| `csrc/flash_attn/src/flash_fwd_kernel.h` | the forward kernel | 4 lines |
| `csrc/flash_attn/src/flash_fwd_launch_template.h` | which instantiation is launched | 3 hunks |

Both of the files that do differ are irrelevant here:

- `flash_fwd_kernel.h`: the only change is `Kernel_traits::TiledMma` to
  `typename Kernel_traits::TiledMma` in four places, a dependent-type spelling fix. The
  generated code is the same.
- `flash_fwd_launch_template.h`: the launch adds `&& !Has_alibi` to the IsEvenMN argument and
  `&& !ReturnSoftmaxConst && !Has_alibi` to the IsEvenK argument, and drops head dim 160.
  `scaled_dot_product_attention` exposes neither ALiBi nor return_softmax, so both are false on
  this path and both added conjuncts are true, leaving the same template arguments; head dim
  160 is not measured here.

So on this path - fp16, head dim 64 or 128, no dropout, no ALiBi, no soft cap, no local window,
sm_89 - upstream FlashAttention-2 has not changed since the version PyTorch vendors, and the
baseline in these tables is the current one.

Not settled by this: PyTorch adapts the kernels when it vendors them, so its copy could in
principle differ in speed from an upstream build. Measuring that needs `flash-attn` built from
source against torch 2.10, for which no wheel exists; three source builds were attempted and
each exhausted this WSL instance's 7 GB and took the WSL service down with it, so it was
dropped rather than risk the vLLM environment. It belongs on a machine with more memory.
